# Chog City Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. **Goal:** Build a shared, agent-run city builder where Chogs gather resources and develop plots autonomously while NFT holders watch and change three settings.

**Architecture:** An independent `city/` package contains a React observation UI, Fastify API, PostgreSQL world/ledger/outbox, and a deterministic simulation scheduler. Fixture mode delivers the first playable village without public RPC; a `ChainReader` port later connects verified Awakening bindings. One atomic city tick applies game effects and public events; no wallet execution or model call belongs inside that transaction.

**Tech Stack:** Node 24, TypeScript, React, Vite, Fastify, Zod, PostgreSQL/pg, ethers 6.17.0, Vitest/Testing Library, Playwright. Proposed dependencies; pin compatible versions/lockfile at implementation.

**Spec:** [Chog City design](../specs/2026-10-19-chog-city-design.md). Read it with this plan. Deployment recovery context: [Claude handoff](../../../CLAUDE_HANDOFF.md).

## Global Constraints

- The user chose a mix of an agent world and a city-building game, with holders able to view and make a few settings.
- Build inside independent `city/`, with its own package/lockfile, config and tests. No new Solidity contract is required.
- Leave the root Solidity code, root lockfile and root `.env` to Claude.
- All uint256 IDs are canonical decimal strings, including `"0"`; validate the uint256 maximum, not just string length.
- Wood, stone and food are noncash integer game resources. Production and construction consumption form the first economy.
- The persistent agent policy continues while the holder is offline or signed out. Logout ends the human session; Pause stops the Chog.
- Every effective policy change/transfer cancels unfinished construction and releases its reservations exactly once. Public completed state and unspent inventory persist.
- No network or inference call while holding a SQL lock.
- Fixture mode requires no root `.env`, RPC, wallet or model key and is local dev/test only.
- Mainnet, tradable land/tokens, inference spending and external social-account execution are outside this release.

## Review Focus

1. **Resource duplication or partial construction after a crash/retry:** pinned by Task 4 race/lost-response/rollback tests.
2. **A→B→A ownership or settings changes reviving stale activity:** pinned by Tasks 5 and 9 epoch/policy tests.
3. **Tick, reserved inventory and building progress drifting across restart or downtime:** pinned by Tasks 2, 4 and 11 replay/catch-up tests.
4. **Snapshot/reconnect skipping events because revision allocation differs from commit order:** pinned by Task 8 concurrent snapshot/replay tests.
5. **Demo controls or stale RPC observations entering live authorization:** pinned by Tasks 5, 6 and 9 startup/identity/unavailability tests.

### Shared contracts to freeze in Task 1

- `makeAgentKey(identity: AgentIdentity): AgentKey` uses the full tuple from the spec; lowercases addresses.
- `makeFixtureWorld(options?: {residentCount?: number; active?: boolean}): WorldState`; defaults 8 residents, active scripted demo, fixed seed. First resident has token/agent ID `"0"`.
- `WorldState = {cityId, tick, seed, rulesetVersion, places, plots, agents}`. Numeric IDs/tick use strings; resource quantities use bounded integers.
- Each `AgentState` has `{key,identity,control,controlAvailability,plotId,location,policy,inventory,homeLevel,homeStyle,construction,lastGreetingTick}`; inventory maps each resource to `{total,reserved}`. `control` is the spec's CanonicalControlState (kind, controller/null, epoch, projection generation, block/hash/time). Availability is `verified|unavailable`; unavailable never erases canonical state. This stored state lets pure fixture transitions compare repeated observations and lets getMyAgents switch A/B ownership.
- `Construction = {actionId,targetLevel,costs,remainingTicks,policyVersion,ownershipEpoch,startedTick}` or `null`.
- `LedgerEntry = {agentKey,resource,totalDelta,reservedDelta,causeId,lineId,reason}`; deltas are signed integers, reason is `admission|gather_input|gather_output|build_reserve|build_consume|build_release`. Unique `(city_id,causeId,lineId)`; cause identifies one stable action/admission/policy change and lineId identifies resource+reason. Reserve is `0/+cost`, consume `-cost/-cost`, release `0/-cost`, grant/production `+yield/0`; gather input is `-cost/0`.
- `Actor = {sessionId,address}` is server-authenticated, never copied directly from an arbitrary request body. `TickCommit = {tick,revision,inputHash,resultHash,actionCount}`; string IDs/revisions, integer action count.
- `PlaceId = 'plaza'|'tavern'|'workshop'|'forest'|'quarry'|'farm'`; location is `{kind:'place',placeId}` or `{kind:'plot',plotId}`.
- `step(input: TickInput): TickResult`, `applyPolicyChange(world,key,nextPolicy): TickResult` and `applyControlChange(world,key,observation): TickResult` are pure. Return typed effects/ledger entries/public changes; never mutate input objects.
- `CityClient` web port: `getSnapshot()`, `getAgent(key)`, `getMyAgents()`, `updatePolicy(key,request,idempotencyKey)`, `subscribe(afterRevision,onEvent,onReset): () => void`. Fixture and HTTP clients share DTOs.
- `PolicyUpdateRequest = {expectedVersion,expectedEpoch,active,focus,homeStyle}`; `CitySnapshot = {revision,tick,nextDueAt,world,recentEvents}`.
- `CityEvent = {revision,type,data,createdAt}`; type is `city_tick|policy_changed|control_changed|resident_admitted|simulation_gap`. Each type has its own strict public payload schema.

`ChainReader.resolveAgent(identity)` and `ControlObservation` use the exact union in the spec, including observedAtMs/projectionGeneration for all canonical results. Unchanged epoch/generation/status reconciliation is idempotent; unavailable is a transient freeze. If a task needs another cross-file interface, update this contract section and its tests before implementing its consumer.

## 4. Expansion after the first playable village
